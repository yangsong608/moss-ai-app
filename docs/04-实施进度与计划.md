|---|---|

| POST /sync/push（写入探针） | ✓ HTTP 200，accepted 含探针 id |
| delta 能拉到刚推的探针任务 | ✓ |
| POST /sync/push（删除探针） | ✓ HTTP 200 |

**首次运行曾失败 1 项（`delta 能拉到刚推的探针任务`）**，根因是脚本自身、不是链路：

`e2e-sync.mjs` 用 `new Date().toISOString().replace('T',' ').slice(0,19)` 生成 `updatedAt`，在东八区得到的是 **UTC 时间**（16:46），比 delta 游标（21:48 本地）早 5 小时。宿主 `syncPush` 的 `normalizeTime` 只校验非空、原样落库，而 delta 用**字符串字典序**比较 `updated_at > since`，于是行虽落库但落在游标之前，永远拉不到 —— 正是 `dsh-workbench/docs/sync-protocol.md` §7 明令禁止的 ISO 写法。改为本地时间 `YYYY-MM-DD HH:MM:SS` 后全通过。

**并发注意**：DSH 一直持有该 SQLite（WAL），外部 `sqlite3` 写入会报 `attempt to write a readonly database`；验收探针请一律走 `/sync/push` 接口，不要直连库改数据。

### 5.2 跨天区间映射（P1-3 补完）

`sync-adapt.ts` 原先只推 `date/start`、`end` 恒为空串，跨天任务同步后丢区间。宿主 tasks 表虽然没有 `startAt/endAt` 列，但 `date + start + end + duration` 四列足以无损还原，因此按以下口径映射：

| 方向 | 规则 |
|---|---|
| 本地 → 行 | 有 `startAt/endAt`：`date`=**起始日**、`start`/`end`=起止 `HH:MM`、`duration`=总分钟数；无区间时维持原行为（只写 `start`、`end` 空、`duration` 0），不凭空发明时间 |
| 行 → 本地 | `end <= start` 判定跨到次日（22:00→08:00）；`duration` 比 `end` 更权威（相差 > 1 分钟时以 `duration` 为准，宿主日历块按它画）；只有 `start` 时按 1 小时补齐（与 `workbench.taskSpan` 同口径）；无 `start` 或无 `date` 视为未排期，不给区间 |

两处易踩的坑已固化为断言：

- **`startAt`/`endAt` 必须总是出现在返回值里**（无区间时为 `undefined`）。同步走 `Object.assign(local, fromRow(...))`，字段缺省会让本地残留旧区间——远端把任务改成「未排期」后本地会一直显示旧时间。
- **宿主存量行有 `end` 为空、`duration` 有值**（如 seed-1：`14:00` / `end=''` / `duration=45`）。只按 `end` 解析会退化成 1 小时并把它写回，时长被悄悄放大。实测该行往返后仍为 45 分钟。

真实链路验证（跨天探针经宿主往返）：

```
本地 22:00→次日08:00 → 行 {date:'2026-10-26', start:'22:00', end:'08:00', duration:600}
→ push accepted → delta 拉回 → 行→本地 startAt 2026-10-26 22:00:00 / endAt 2026-10-27 08:00:00
区间无损 ✅（600 分钟）
```
