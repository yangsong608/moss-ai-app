# MOSS AI App · 可行性分析（v1 草案）

> 日期：2026-10-24 ｜ 关联：[02-技术架构](02-技术架构.md) ｜ [03-产品设计](03-产品设计.md)
> 方法：对 dsh-link-suite（协议/网关）、dsh-workbench（API/存储/同步语义）、moss-ai-app（现状）三侧源码实证 + 逐条需求判定

## 0. 结论（先说答案）

**可行，且大部分能力是"接线"而非"造轮子"**——任务/日历/专注/新闻/笔记的数据模型、AI 工具、定时链路在 dsh-workbench 里都已存在，手机端要新造的是：本地存储层 + 同步引擎 + 多设备域模型。真正的工程风险集中在**一处**：dsh-workbench 现有写入模型（整份快照 + 单 revision + 无 tombstone）**不能直接用于多端写**，必须先做增量协议改造，否则手机与 PC 会互相冲掉数据。这是 M2 的前置门槛，不是可选项。

| 需求 | 判定 | 依据摘要 |
|---|---|---|
| 移动端任务/日历/专注/新闻/笔记 | ✅ 可行 | 数据模型与业务规则已有（工作台五模块），手机是新 UI + 裁剪 |
| 手机本机存储（SQLite） | ✅ 可行 | App 端 `plus.sqlite`；H5 用 IndexedDB 适配（数据量小） |
| 与同设备 DSH 双向同步 | ⚠️ 可行，需先改造工作台 | 现状快照 LWW 互踩、无 tombstone、无增量端点（见 §3） |
| 调用 DSH AI agent 对话/执行 | ✅ 可行 | 现有 `session.*` 12 个方法已覆盖（create/prompt/follow/answer…） |
| 多设备各自独立数据域 | ✅ 可行 | 协议/会话天然 per-host；手机侧加 `_device` 分区即可 |
| 新闻定时/摘要 | ✅ 可行 | `/dsh-cron` type:'llm' 链路已在工作台跑通，手机只管订阅与查看 |

## 1. 需求拆解与现状对照

1. **任务/日历/专注/笔记的业务逻辑**：工作台 v1.10.0 已完整实现（六投影、番茄计时、MD 笔记、AI 完善回写），手机端不需要重新定义业务，只需移动裁剪（见 03-产品设计 §3）。
2. **新闻**：订阅→cron→LLM→`workbench_news_publish`→去重/截断/限量的闭环已存在；手机增量是"订阅管理 + 瀑布流查看 + 立即检索"。
3. **AI 对话**：dsh-link 已实现会话转发（流式、工具过程、审批、队列、genui 子集）——升级点只在"上下文携带"（任务/笔记引用）。
4. **多设备独立**：`session.list` 等本来就按宿主实例隔离；数据侧手机按 `deviceId` 分区存储，聚合视图只读。

## 2. 技术可行性逐项

### 2.1 移动端本地存储 ✅
- App：`plus.sqlite`（uni-app 官方 API，事务/索引够用）；H5：IndexedDB（localStorage 只做兜底/小数据）。
- 风险：**两端存储能力不一致**——用 StorageAdapter 抽象（接口：事务写、游标查询、按域分区），业务层不感知差异。工作量可控（一层适配）。
- 体量估算：单设备任务 1k 条 + 笔记 200 篇 ≈ 5–20MB，移动端无压力。

### 2.2 双向同步 ⚠️（核心风险区）
现状实证（dsh-workbench）：
- `PUT /state` = **整份快照**：事务内 7 表全清 + 重插，单 `revision` 乐观锁（index.ts:545-546, 617）；409 时前端整份覆盖本地并**丢弃本地未保存修改**（app.ts:662-675）。
- **删除无 tombstone**：软删字段 `deleted_at` 不被 writeState 保留，删除=物理消失，无法跨端传播。
- **无增量端点**：没有 `?since`；tasks/spaces/notes/news_topics 有 `updated_at`，subtasks/logs/focus_sessions 没有。
- `/workbench-api` **无鉴权**（挂在 DSH webServer 同源端口，index.ts:37, 4206-4208）。

判定：**双向同步在"手机↔单 PC"尺度可行**，但必须按 [02-技术架构 §5](02-技术架构.md) 先给工作台补三件套：tombstone 表、增量 delta 端点、条目级 push 写入口。做完后语义 = 最终一致 + LWW + 冲突副本，对任务/笔记类产品足够（Notion/滴答同类产品同级语义）。
- 若跳过改造直接同步：两台写入方会互相覆盖全库（现有 409 流程本来就会丢手机离线修改）——**判定为不可接受，必须改造**。

### 2.3 协议/网关扩展 ✅
- 协议有完善的纪律体系：方法白名单 + 每方法策略 + 能力协商 + 编译期 `Record<Method,Handler>` + 自检测试（"每个方法都有策略"等 24 项）——新增 `wb.*` 方法组是**模板化施工**（9 步清单已列）。
- 网关有软读服务惯例（`ctx.get(name,false)`）、既有适配层样例（adapters/changes.ts、sessions.ts）；调工作台走 loopback HTTP 可行（`/workbench-api` 无鉴权、回环可达）。
- 约束：控制帧 256KB → delta 分页；写方法需 `operator/unlocked`（锁屏语义一致）。

### 2.4 多设备并发 ✅
- 网关允许同设备多连接；per-IP 8 / 全局 64——手机常驻 3–5 条设备连接在预算内。
- 会话/锁态/caps 天然逐 host 独立；App 侧要做的是 LinkPool（多连接管理）与 token 分设备保管（keychain）。
- 唯一注意：建连限速 10 次/分/IP，同步失败必须退避而非重连补帧。

### 2.5 AI 能力 ✅
- 对话/派发/回写全链路已存在（session.* + workbench_* 工具 + cron）；手机只需发 prompt、收流式、展示 genui 子集（两轮渲染修复已落）。
- 新闻"立即检索"= 触发现有 LLM cron 任务，不需要新造抓取器。

### 2.6 打包与发布 ✅（有旧账要还）
- HBuilderX 打包 App；**iOS 局域网权限 `NSLocalNetworkUsageDescription` 必须补**（不声明静默失败——迁移盘点已记录，属本地上线前置）。
- 协议双份同步（moss-ai-app/protocol ↔ dsh-link-suite/shared/protocol）是既有约定，升级期要严格双侧同改 + 双侧测试。

## 3. 风险矩阵

| # | 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|---|
| R1 | 快照写入模型导致双端互踩 | 高（现状必然） | 数据丢失 | **前置改造**：delta/tombstone/条目 push（工作台 M2-0）；改造前手机端只读上线（M1） |
| R2 | 删除无法传播（无 tombstone） | 高 | 脏数据回流 | tombstone 表 + 30 天回收站产品化 |
| R3 | 协议双份漂移（app/protocol vs shared/protocol） | 中 | 联调失败 | 双侧同改 + 各自 test:protocol + 联调前 diff methods |
| R4 | 256KB 帧限制 | 中 | 大笔记同步失败 | delta 分页 + 大正文分块/BIN_FILE |
| R5 | H5/App 存储能力差异 | 中 | 功能不一致 | StorageAdapter 抽象 + H5 降级策略明示 |
| R6 | 旧网关无 wb.* 方法 | 高（存量设备） | 新 App 连旧网关报错 | caps 协商降级：`host/unavailable` → 隐藏新模块，保持遥控器功能 |
| R7 | /workbench-api 无鉴权 | 低（回环） | 越权访问 | 同步一律走网关 RPC（手机不可直连）；工作台加 loopback 校验 |
| R8 | iOS 权限缺失 | 高（未补前） | 局域网直连静默失败 | manifest 补权限 + 真机验收清单 |
| R9 | AI 回写与手机编辑竞态 | 中 | 一方覆盖 | AI 回写也走 delta（updated_at LWW），冲突副本兜底 |
| R10 | HBuilderX 构建链在本机缺失 | 中 | 发不了 App | 发布走 HBuilderX 机器；本机只出 H5 验证包（既有约束） |

## 5. 分期与退出点

| 期 | 范围 | 前置条件 | 退出点（不达标就停） |
|---|---|---|---|
| M1 本地先行 | 五模块本地版 + 现有 dsh-link 会话能力 | 无 | 本地全功能可用、H5/App 双包通过——此时产品已可用（单机版） |
| M2 双向同步 | WP1+WP2+WP4、多设备域 | WP1 完成 | 双端 30s 内互见、断网重连不丢不重、冲突不静默丢 |
| M3 AI 深化 | WP6 + 新闻订阅管理 | M2 稳定 | "手机说、电脑干、手机看结果"闭环验收 |

**降级路线**（始终可用）：若 M2 改造延期，产品可停在 M1 + "会话遥控器"形态发布——五模块手机本地独立可用，只是不与 PC 同步；不阻塞上线。

## 6. 结论

1. 需求成立、技术路径清晰；**AI 对话/新闻/多设备会话是现成能力的重新组合**，风险低。
2. 唯一硬前置是 **dsh-workbench 写入模型改造**（快照→增量 + tombstone）；它同时也是工作台自身多开/多端的正确性前提，属于"迟早要做"的债。
3. 总量 ≈12.5 人周，可按 M1（本地可用）→ M2（同步）→ M3（AI 深化）分三期交付，每期都有独立退出点与降级路线。
